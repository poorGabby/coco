# CoCo MCP 升级：对话即接入 —— 可插拔数据源 + 文档读写

> 状态：计划中（2026-07-20）
> 关联：`.cursor/rules/coco-agentic-north-star.mdc`、`plans/2026-07-15 CoCo 受控 Agentic 升级.md`
> 主线：CoCo = 接入飞书的企业级 agentic 机器人（日报 / 知识库 / 问答 / 取数 / 分析 / 执行指令）

## 1. 目标 / 非目标

**目标**：让运营/开发**只在飞书私聊里对话**，就能让 CoCo：
- 自动接入新的数据源（新的 API / SaaS / 数据库），无需每次改 agent 内核代码；
- 读取文档（飞书 wiki / Notion / 其他知识源）；
- 写出文档（把分析、结论、日报归档成飞书/Notion 页面）；
- 上述能力都以 **LLM 自主判断意图 → 调用工具** 的方式发生，不加关键词分支。

**非目标（本阶段明确不做）**：
- 不做"用户在聊天里贴一段任意 API 文档，CoCo 就凭空联通任意系统"的全动态联通——鉴权/schema/安全风险过高。
  取而代之：**接入 = 从受控白名单里"启用"一个已登记的 MCP server / REST 源**，密钥走安全通道注入，不进聊天。
- 不替换现有日报工程管道；MCP 只扩展"自由问答 + 指令执行"这条链路。

## 2. 现状（已具备的基础）

- **Agentic 内核已就位**：`src/llm.ts::generateWithTools` 是 Gemini function-calling 循环，模型自主选工具。
- **工具注册表**：`src/agent/tools.ts::buildToolRegistry(env)` 把声明映射到后端实现。**这是 MCP 工具的天然挂载点。**
- **口径外置**：`src/agent/skill-doc.ts::resolveSkillDoc` 从飞书 Skill 文档动态加载规则（Phase 5）。
- **文档读取**：`src/feishu.ts::getDocumentRawContent` 已能读飞书文档。
- **开关/回退范式**：`HERMES_AGENT_ENABLED`、Stripe 缺失回退 Amplitude —— 新能力沿用此范式灰度接入。

关键结论：**瓶颈不是模型，是"每加一个能力=加一段代码"**。MCP 的价值就是把它变成"注册一个 server"。

## 3. 架构总览

```
飞书私聊 → index.ts → answerFreeform → runAgentQuestion
                                   │
                                   ▼
                    generateWithTools (Gemini function-calling)
                                   │
                     ┌─────────────┴──────────────┐
             本地原生工具                    MCP 工具（运行时发现）
        (fetch_daily_revenue…)        ┌────────┬────────┬─────────┐
                                   Feishu   Notion   自定义REST  数据库
                                   MCP      MCP      -MCP        -MCP
```

- 新增 **MCP client**（`src/agent/mcp/`）：启动时连接"已启用"的 MCP server，拉取它们暴露的 tools，
  转成 Gemini function-declaration，**合并进 `buildToolRegistry` 的 registry**。对模型而言，MCP 工具与本地工具无差别。
- **server 清单来自配置**（env + 飞书 Skill 文档的一段结构化区块），支持热更新，不改代码即可增删源。
- **文档写入**作为一类工具：飞书页面用 Feishu 开放平台创建/更新接口封装成原生工具或本地 MCP server；
  Notion 直接用现成 Notion MCP server。

## 4. 分阶段实施

### Phase A — MCP client 接入内核（1 个 PR）
- 加依赖 `@modelcontextprotocol/sdk`（Node client）。
- `src/agent/mcp/client.ts`：连接一个 stdio/HTTP MCP server，`listTools()` → 缓存；`callTool(name,args)`。
- `src/agent/mcp/registry.ts`：把 MCP 工具声明转 Gemini schema，注入 `buildToolRegistry` 返回的 registry；
  工具名加命名空间前缀（如 `mcp__notion__search`）避免与本地工具冲突。
- 开关：`HERMES_MCP_ENABLED`（默认关，灰度）；关掉即完全等价于现状。
- 验收：本地起一个示例 MCP server，问答能自动调用其工具；关闭开关行为不变。

### Phase B — 配置化 server 清单（1 个 PR）
- server 定义来源：①env `HERMES_MCP_SERVERS`（JSON：name/transport/command/url）②飞书 Skill 文档中一段
  `## MCP 数据源` 结构化清单（只放非敏感元数据）。
- **密钥安全**：凭证只走 `.env` / Cloud Run env / Secret Manager，用占位符 `${STRIPE_KEY}` 在配置里引用，
  **绝不写进聊天或飞书文档**。
- 热加载：复用 `skill-doc.ts` 的 TTL 缓存范式，改文档 60s 内生效。
- 验收：仅编辑飞书文档 + 配好密钥，即可让新 REST 源上线，无需发版。

### Phase C — 文档读写能力（1 个 PR）
- 读：接入 Notion MCP（现成）+ 保留飞书 `getDocumentRawContent`；统一成 `read_doc` 语义工具。
- 写：`src/feishu.ts` 增加创建/更新飞书文档的封装 → 暴露为 `write_feishu_doc` 工具（或做成本地 MCP server）。
- 场景：私聊"把刚才的分析归档成一篇飞书文档" → 模型调 `write_feishu_doc` 生成页面并回链接。
- 验收：一句话让 CoCo 生成并回传一篇飞书/Notion 文档链接。

### Phase D — 对话式接入（受控）（1 个 PR）
- 指令入口（自然语言，非硬编码关键词；靠工具描述让模型识别）：
  - `list_data_sources`：列出可启用的白名单 server 与已启用状态。
  - `enable_data_source(name)`：把白名单里的 server 标记启用（写入运行时状态/配置），并提示"密钥请管理员在安全通道配置"。
- 全动态"贴 API 即接入"仅作为**受管理员确认**的实验特性，且限制在只读、带 schema 校验、需二次确认。
- 验收：私聊"接入 Notion" → CoCo 启用并可立即读写 Notion 文档。

### Phase E — 治理与安全（贯穿，独立 PR 收口）
- **权限分级**：只读工具可直接调；写/删/外发类工具需**二次确认**（飞书交互卡片按钮）。
- **白名单**：只有登记过的 server/工具可被启用；未知源默认拒绝。
- **审计日志**：每次工具调用记录 who/what/args 摘要/结果状态（复用现有 `[agent]` 日志）。
- **限流与超时**：MCP 调用统一超时/重试，失败回退到"仅本地工具"，保证不瘫痪。

## 5. 与现有代码的融合点（不割裂）
| 现有 | 接入方式 |
|---|---|
| `agent/tools.ts::buildToolRegistry` | MCP 工具 merge 进同一 registry，模型无感 |
| `llm.ts::generateWithTools` | 不改循环，只是工具变多 |
| `agent/skill-doc.ts` | 复用其飞书文档 + TTL 缓存承载 server 清单 |
| `feishu.ts` | 复用鉴权 token，扩展文档写接口 |
| 开关范式 | `HERMES_MCP_ENABLED` 灰度，缺省关=现状 |

## 6. 风险与回退
- **安全**：密钥绝不入聊天/文档；写操作需确认；白名单化。→ 出问题关 `HERMES_MCP_ENABLED` 即回退。
- **稳定**：MCP server 挂掉不能拖垮问答 → 连接失败/超时静默降级到本地工具。
- **成本/延迟**：工具变多会增加模型 token 与轮次 → 用命名空间 + 精简描述 + 每问最大工具轮次上限控制。

## 7. 里程碑
- M1（Phase A+B）：MCP 内核 + 配置化清单 —— "改文档/配密钥即接入新源"。
- M2（Phase C）：文档读写 —— "一句话归档成飞书/Notion 文档"。
- M3（Phase D+E）：对话式启用 + 治理 —— "私聊即启用白名单数据源，写操作有确认与审计"。

> 北极星复述：能力=可插拔工具/MCP server，意图交给 LLM，口径与清单外置到文档，一切新增走"注册/配置"而非改内核。
